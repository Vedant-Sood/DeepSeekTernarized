# M2 report: packing formats, ternary kernels, Mode C

Date: 2026-11-03. Status: the code is done and the tests pass. On the real weights, plain
(no-calibration) Mode C k=2 is **not yet "close to the baseline"**: GPTQ is needed, and the quality
numbers below say how far off it is.

All numbers here were measured in this container (4 CPU cores with AVX2/AVX-512, 15 GB RAM, no
GPU). Full-model sizes are computed from the real shard headers × the measured bits per weight,
and are labelled as such.

## What was built

| Piece | Where | What it does |
|---|---|---|
| TQ2 / TQ1 packing | `boilerplate/ternary/pack.py` | 4 trits per byte (2 b/w) and 5 trits per byte in base 3 (1.6 b/w). Layout in `docs/architecture/format.md` |
| Stacked ternary fit | `boilerplate/ternary/fit.py` | `fit_residual`: k greedy terms on the residual. Each term is the least-squares optimum per (row, group), found exactly by sorting. `fit_gptq`: GPTQ column sweep with stacked-ternary rounding, scales fixed per group |
| Ternary linear | `boilerplate/ternary/ops.py` | int8 per-token absmax activations (or BF16); runs k passes of the C++ kernel, or a PyTorch dequantized fallback |
| CPU kernel | `boilerplate/kernels/csrc/boilerplate_cpu.cpp` | `ternary_gemm`: decodes each packed row to int8 trits once per call, then an add/subtract inner loop (AVX2 `_mm256_sign_epi8` + widening adds, no multiplies), one FP multiply per group for the scale. OpenMP over output rows. Scalar fallback elsewhere. JIT-built with `-march=native` |
| Policy | `boilerplate/format/policy.py`, `configs/policy/*.yaml` | Regex rules → mode / k / group / packing / scale dtype / activation mode / GPTQ. Refuses a Mode C setting that does not shrink its source (≥ 0.85x its bits) unless `allow_larger` |
| Export + format | `boilerplate/format/export.py`, `docs/architecture/format.md` | `boilerplate export SRC OUT --policy P.yaml [--calib-text F]`: sharded safetensors + `manifest.json` (architecture, per-tensor mode, packing, group, scale dtype, SHA-256, effective bits per weight) |
| Calibration | `boilerplate/format/calibrate.py` | Runs the Mode A engine on calibration text and collects `H = XᵀX` per expert input (w1/w3 share one) |
| Engine | `boilerplate/engine/model.py`, `weights.py` | Loads Mode C linears and Mode C engram tables (rows are unpacked on lookup) straight from the manifest |

## Bits per weight

Mode C costs `k × (packing bits + 16 / group)`. The release stores routed experts as FP4 with one
e8m0 scale per 32 weights, which is **4.25 b/w** (checked against the shard headers). That sets
what Mode C can save:

| setting | b/w | vs FP4 experts |
|---|---|---|
| TQ2 k=2, g128 | 4.25 | 1.00x, refused by the policy |
| TQ1 k=2, g128 | 3.45 | 0.81x |
| TQ1 k=2, g256 | 3.325 | 0.78x |
| TQ1 k=1, g128 | 1.725 | 0.41x |

Measured on the export of the real slice (`manifest.json` summary): the experts came out at
3.450 b/w for k=2 and 1.725 b/w for k=1.

### Whole model, both engram policies (projected from the headers)

Bytes per role are taken from the release's shard headers. Ternarized roles are multiplied by the
measured Mode C bits per weight. Generation weights only (the MTP heads and the vision tower, 1.5 GB,
are not counted).

| policy | routed experts | engram tables | rest | total | b/w overall |
|---|---|---|---|---|---|
| Mode A (release) | 296.0 GB | 202.8 GB | 10.0 GB | **508.8 GB** | 5.34 |
| `experts_k2` (TQ1 k=2) | 240.3 GB | 202.8 GB | 10.0 GB | **453.1 GB** | 4.76 |
| `experts_k1` (TQ1 k=1) | 120.1 GB | 202.8 GB | 10.0 GB | **332.9 GB** | 3.49 |
| `experts_engram_k2` (TQ1 k=2 on both) | 240.3 GB | 84.8 GB | 10.0 GB | **335.1 GB** | 3.52 |
| experts + engram TQ1 k=1 | 120.1 GB | 42.4 GB | 10.0 GB | **172.5 GB** | 1.81 |

So "with engram" is where most of the size goes. Ternarizing the experts alone at k=2 saves only
11%, because they are already FP4.

## Quality

### Real 7-layer slice (layers 0, 1, 2, 3, 20, 21, 24 of the release; 16 experts per layer)

The comparison is against Mode A on the same slice, over 1,024 WikiText-2 test tokens. The slice
is not a working language model: its own perplexity is ~8 million, because 33 layers and 368/384
experts are missing. So absolute perplexity means nothing here. The meaningful numbers are how far
each layer's output drifts from Mode A (`scripts/eval/m2_eval.py`).

| | layer 1 | 2 | 3 | 4 | 5 | 6 | 7 (last) | logits KL | top-1 agree |
|---|---|---|---|---|---|---|---|---|---|
| TQ1 k=2, plain | 0.9995 | 0.9979 | 0.9949 | 0.9895 | 0.9759 | 0.9742 | **0.9663** | 0.38 | 51% |
| TQ1 k=1, plain | 0.9982 | 0.9940 | 0.9865 | 0.9720 | 0.9425 | 0.9349 | **0.9157** | 0.93 | 24% |

(Hidden-state cosine to Mode A, averaged over tokens.) The error grows about linearly with depth.
Over 40 layers, plain k=2 would not be close to the baseline. The top-1 and KL numbers come from a
near-uniform output distribution (NLL ≈ 15.9 nats, above the uniform 11.8), so they overstate the
disagreement a real model would show. They are kept here to be complete, not as a quality claim.

### GPTQ on real expert inputs

Layer 2 of the slice, 4 experts × (w1, w2, w3). Calibration used 8 × 512 WikiText-2 *train*
tokens. Evaluation is on held-out *test* inputs. The metric is the relative output error
`‖X(W−Q)ᵀ‖² / ‖XWᵀ‖²` on the expert's real inputs.

| | plain fit | GPTQ | reduction |
|---|---|---|---|
| TQ1 k=1 | 0.152 | 0.098 | −36% |
| TQ1 k=2 | 0.0363 | 0.0224 | −38% |

GPTQ helps most on w1/w3 (the gate and up projections, up to −77%), and least on w2 (0 to −42%).
I have not yet run GPTQ on the whole slice end to end. That needs a Hessian per expert input
(about 120 MB each in FP32). On this machine that fits per layer, not all at once (`--calib-layers`
exists for that).

### Engram tables (real rows)

From 2 × 131,072 rows sampled at random from both real tables (`layers.1/14.engram.embed`, fetched
with HTTP range requests). The source is FP8 with 1×32 scales, 8.25 b/w.

| setting | b/w | rel. error | row cosine (mean / 1st pct) |
|---|---|---|---|
| TQ1 k=1 g128 | 1.725 | 0.433 | 0.901 / 0.881 |
| TQ1 k=2 g128 | 3.45 | 0.200 | 0.981 / 0.970 |
| TQ1 k=2 g256 | 3.325 | 0.202 | 0.981 / 0.969 |
| TQ1 k=3 g128 | 5.175 | 0.123 | 0.993 / 0.987 |

Both tables behave identically. Their rows are added to the hidden state after a learned gate.
How much row error the model tolerates has not been measured end to end: the slice has no
engram, because the tables are 100 GB each. On the tiny model the engram path runs and loads
correctly (test `test_mode_c_export_and_run[True]`).

### Tiny model

Tiny's weights are random Gaussians, so its quality numbers are not meaningful. It is used to
check that every mode exports, loads and runs, and that the manifest is complete.

## Speed (CPU, 4 threads, real slice, prompt 128, 8 decode steps)

| | load | prefill tok/s | decode tok/s | peak RSS |
|---|---|---|---|---|
| Mode A | 1.7 s | 2.62 | 0.064 | 8.4 GB |
| Mode C TQ1 k=2 | 2.1 s | 3.46 | 0.164 | 8.1 GB |

Both are slow because Mode A's FP8/FP4 path on CPU is the PyTorch reference kernel. It
dequantizes each weight on use; the hot weights are cached. These numbers show the ternary path
is not a bottleneck. They are not an optimized speed comparison, which needs the GPU kernels
(not built yet).

## Tests

`tests/test_ternary.py` and `tests/test_format.py` add 45 tests:

- TQ1/TQ2 round-trips for odd K, and all 243 TQ1 byte patterns.
- Optimality of the single-term fit against brute force.
- Error decreases monotonically in k.
- GPTQ lowers output error on correlated inputs.
- int8 activation bounds.
- The C++ kernel matches the dequantized matmul (both packings, int8/BF16 activations, groups 64/128/256, ragged K).
- Policy parsing and the size guard (TQ2 k=2 on FP4 experts is refused).
- Mode C export → manifest → engine for both engram policies, with reconstruction error checked against the source.
- Mode B tests (see M3).

The whole suite: 105 passed.

## Not done / next

- **NEON path**: not written yet. The kernel has AVX2 plus a portable scalar fallback, and ARM
  uses the fallback today. There is no ARM machine here to test a NEON loop on.
- **AVX-512** is used only through `-march=native` auto-vectorization of the scalar parts. The
  hand-written path is AVX2.
- **GPU ternary kernel** and grouped expert GEMM: not started. They need a GPU; ZeroGPU sessions
  are too short for development.
- **End-to-end GPTQ** over the slice, then the full model (offline: the plain fit alone took 623 s per
  4 G expert params here, about 24 h for all 557 G on this CPU; much faster on a GPU).
- Mode C's quality target for the full model has to be judged on real evals (WikiText-2 / C4
  perplexity, lm-eval) after the full conversion in M5. The slice cannot answer it.
