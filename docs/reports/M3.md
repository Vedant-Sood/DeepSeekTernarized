# M3 report: Mode B, lossless entropy coding

Date: 2026-11-03. Status: CPU correctness demonstrated; runtime work remains. The original Mode B
implementation was **bit-identical to Mode A** through the engine on the real 7-layer slice and
tiny model. The subsequently added on-demand CPU cache has been checked on tiny but not yet on
the real slice. A CUDA decoder prototype is unvalidated; see below.

## What was built

| Piece | Where | What it does |
|---|---|---|
| Codec | `boilerplate/format/entropy.py` | Canonical Huffman over bytes, codes limited to 12 bits, independent blocks of 4096 symbols with bit offsets, decode by a single 4096-entry table lookup |
| Kernels | `boilerplate/kernels/csrc/boilerplate_cpu.cpp` | `huff_encode`, plus `huff_decode` with OpenMP over blocks. The layout (one table, per-block offsets, MSB-first) is the one a GPU decoder of one thread block per block needs |
| Format | `boilerplate/format/export.py`, `docs/architecture/format.md` | `T.hstream / T.hoffsets / T.hlens / T.hraw` per tensor, with dtype and shape in the manifest |
| Engine | `boilerplate/engine/weights.py` | A Mode B tensor is decoded back to its exact original bytes on first use, then goes through the Mode A path unchanged |
| Policy | `configs/policy/lossless.yaml` | Every weight Mode B |

What gets coded: for 1-byte formats (FP8 e4m3, packed FP4 pairs, e8m0 scales), every byte. For
BF16/FP16, the high byte (sign, exponent, top mantissa bit), with the low byte stored raw. FP32
tensors are left alone; they total 0.17 GB in the release.

## Gain, measured on the real slice (all 6.0 GB of it)

Every tensor of the 7-layer slice was coded, decoded, and compared byte for byte. All of them
round-trip exactly.

| tensor type | bytes | coded / original |
|---|---|---|
| routed experts, FP4 pairs (int8 storage) | 1.98 GB | **0.977** |
| routed expert scales (e8m0) | 124 MB | 0.176 |
| attention FP8 | 902 MB | 0.827 |
| shared experts FP8 | 248 MB | 0.829 |
| FP8 block scales | 1.1 MB | 0.16–0.18 |
| embedding + head BF16 | 2.65 GB | 0.674 |
| other BF16 | 18 MB | 0.67 |
| FP32 (not coded) | 28 MB | 1.0 |
| **whole slice** | **5.95 GB** | **0.795** (5.87 b/w overall) |

The slice over-weights the BF16 embedding and head, which compress best. The full model is
mostly FP4 experts and FP8 engram, which compress least.

### Engram tables (2 × 131,072 real rows sampled from the release)

| | coded bits per byte | order-0 entropy |
|---|---|---|
| FP8 rows, layer 1 | 6.64 | 6.55 |
| FP8 rows, layer 14 | 6.64 | 6.54 |
| e8m0 row scales | 1.30–1.33 | 0.92 |

So the tables come to 0.83x for the rows, 0.17x for the scales.

### Whole model (projected from the shard headers × the measured ratios above)

| role | release | Mode B |
|---|---|---|
| routed experts (FP4 + scales) | 296.0 GB | 275.1 GB |
| engram tables | 202.8 GB | 164.2 GB |
| everything else | 11.5 GB | 10.2 GB |
| **total** | **510.3 GB** | **≈ 449.5 GB (0.88x)** |

This is the honest ceiling for lossless on this checkpoint. The FP4 experts are already close to
their entropy, so there is about 2% to win there. Huffman codes each symbol in at least 1 bit,
which is why the scales stay above their entropy; rANS would close that gap, but the scales are
only 2% of the file.

## Correctness

- Engine, real slice, 256 WikiText-2 tokens: Mode B logits are **bit-identical** to Mode A
  (KL 0, max-abs 0, `bit_exact: true`).
- Tiny model: same, every layer, plus a byte-for-byte check of every tensor against the source
  (`test_mode_b_bit_exact`).
- Codec unit tests cover uint8, FP8, BF16 and FP16 inputs, and a frequency distribution that
  forces length-limiting past 12 bits (`test_entropy_roundtrip`, `test_entropy_length_limit`).

## Speed (CPU, 4 threads)

| | |
|---|---|
| decode | 532 MB/s of original bytes |
| encode | 32 MB/s (single-threaded encoder + Python frequency count; export-time only) |
| export of the 6 GB slice | 246 s |
| engine, Mode B vs Mode A | prefill 2.60 vs 2.62 tok/s; decode 0.061 vs 0.064 tok/s; load 9.7 vs 1.7 s |
| peak RSS | 12.1 GB vs 8.4 GB |

Today a Mode B tensor is decoded whole on first use and stays decoded in RAM. So it saves disk
and download size, but not memory, and memory is higher than Mode A, which can leave cold experts
on disk through mmap. Saving memory needs decoding per layer or per expert just before use (the
DFloat11 approach) on the GPU. At 532 MB/s on CPU, decoding the 6 experts a token routes to
(about 106 MB of FP4 per layer) costs about 200 ms per layer, which is too slow for CPU decoding. That is a
GPU kernel job.

## Not done / next

- GPU Huffman decode kernel (one CUDA block per 4096-symbol block, with the table in shared
  memory), fused before the FP8/FP4 GEMM, with decoding per layer to save memory.
- Optionally rANS, for the last ~1–2% on scales and FP8.
- Mode B combined with Mode C in one policy (for example, Mode B for attention and embeddings, Mode C for
  experts). See the follow-up below for the tiny-model test; the real slice is not yet tested.

## Follow-up, 2026-11-03: CPU on-demand decode

| Piece | Where | What it does |
|---|---|---|
| Decoded-byte LRU | `boilerplate/engine/weights.py` | Caches decoded tensors or independent Huffman-block ranges under a configurable retained-byte budget. Embedding and engram row reads decode only the blocks they touch. |
| Lazy engine weights | `boilerplate/engine/model.py`, `boilerplate/engine/engine.py` | Keeps Mode B linear weights as references, decodes routed experts when used, and reads the head in chunks. `Engine.load` accepts `mode_b_cache_bytes`. |
| CLI and checks | `boilerplate/cli.py`, `tests/test_mode_b_cache.py` | Exposes the budget on trace/generate/bench; tests cache hits and eviction, byte-exact block-boundary reads and tiny prefill/decode with zero and 8 KiB budgets. |

Tiny random-init checkpoint; Intel Xeon Platinum 8573C cloud CPU, 4-core quota, no GPU,
PyTorch 2.15 CPU, two math threads (`OMP_NUM_THREADS=2`, `MKL_NUM_THREADS=2`,
`MKL_DYNAMIC=FALSE`), batch 1, 128 prompt tokens and 16 decode steps. The budget was 64 MiB
for both processes, with the default FP32 dequantization cache. Both runs of each are shown:

| Run | Mode | Load | Prefill tok/s | Decode tok/s | Peak RSS | Decoded LRU bytes at end |
|---|---|---:|---:|---:|---:|---:|
| Initial | A | 0.124 s | 185.15 | 6.223 | 0.24 million KiB (rounded CLI output) | 0 |
| Initial | B | 0.266 s | 90.52 | 2.498 | 0.25 million KiB (rounded CLI output) | 1,964,494 |
| Remeasure | A | 0.030 s | 392.45 | 20.557 | 247,562,240 bytes | 0 |
| Remeasure | B | 0.148 s | 109.96 | 18.246 | 256,847,872 bytes | 1,964,494 |

The remeasured RSS difference is 9,285,632 bytes, below the 64 MiB budget; it does not establish the
required bound on the 7-layer slice. The limit applies to retained LRU entries, not temporary
decoded tensors, decoder scratch space, the FP32 dequantization cache, allocator retention or
file-backed mmap pages. Large tensors can temporarily exceed the budget. A strict process-RSS
bound is therefore not yet established. The B-vs-A tiny traces were bit-identical in the tests;
GPU and real-slice results are **not run** for the reasons above.

The full test suite passed: **117 tests**, using the same pinned math-thread settings.

### RSS units discrepancy

On Linux, `boilerplate bench` obtains `ru_maxrss` in KiB but divides by 1,000,000 and labels the
rounded result `peak_rss_gb`. The remeasure above printed 0.24 and 0.25 under that label, while
the raw values were 241,760 and 250,828 KiB respectively. Multiplying those raw values by 1024
gives the byte counts in the table. Thus the label understates decimal GB by a factor of 1.024
before rounding. M1 says its RSS figures came from `boilerplate bench`, so those historical
values have the same unit-label issue. The original values are struck through in [M1](M1.md),
which records the corrected tiny-model reruns and the unavailable real-slice rerun. After owner
confirmation, `boilerplate bench` was corrected to report bytes and GiB.

## Follow-up, 2026-11-03: CUDA Huffman decoder prototype

| Piece | Where | What it does |
|---|---|---|
| Optional CUDA extension | `boilerplate/kernels/cuda.py`, `boilerplate/kernels/csrc/huffman_cuda.cpp`, `huffman_cuda_kernel.cu` | One CUDA block per independent Huffman symbol block, with its decode table staged in shared memory. One thread per block walks the variable-length codes; it writes into a reusable output buffer. |
| Decoder interface | `boilerplate/format/entropy.py` | Uses the CUDA extension for CUDA tensors when available, or the CPU decoder and a copy back to the input device when a CUDA toolkit is unavailable. The optional `out` buffer can be reused. |
| Parity checks | `tests/test_huffman_cuda.py` | Compares GPU and CPU output bytes for uint8, packed FP4/int8, FP8, BF16 and FP16, block boundaries and a reused output buffer. |
| Kernel-only benchmark | `scripts/eval/huffman_cuda_bench.py` | Generates synthetic bytes, checks CPU/GPU byte identity, and measures CUDA-event throughput into a reused buffer. It excludes encoding, transfers and table construction. |

CPU-only validation of the decoder interface, cache and existing codec: **17 passed, 11 GPU
tests skipped**. This host has CPU-only PyTorch 2.15, no CUDA toolkit and no GPU. The CUDA source
has **not been compiled or executed**; GPU parity, throughput and VRAM are **not run**. The V4
engine itself is still CPU-only, so the prototype is not yet a GPU Mode B inference path.
The full suite passed **122 tests**, with the same **11 GPU tests skipped**; an offline wheel
build also confirmed that both CUDA source files are packaged. A local attempt to start the
GPU benchmark exited before measuring anything with `CUDA GPU unavailable`.

On an RTX 4060 with CUDA-enabled PyTorch, a compatible CUDA toolkit and the `cpp`, `dev` and
`reference` extras installed, run from the repository root:

```bash
OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 MKL_DYNAMIC=FALSE python -m pytest tests/test_huffman_cuda.py -ra
python scripts/eval/huffman_cuda_bench.py --symbols 16777216 --iterations 20 --threads 4
```

The benchmark's source tensor and output each occupy 16,777,216 bytes, plus the compressed
stream, offsets, table and framework allocations. Runtime and GPU throughput are **not measured**;
elapsed time depends on extension compilation and the measured decode rate. Running on the
owner's existing GPU requires no hardware rental. Engine parity, peak VRAM/RSS and throughput
on the real slice still need a separate GPU engine implementation and real-weight run.

| Piece | Where | What it does |

The validator completed twice on the tiny model on an Intel Xeon Platinum 8573C cloud CPU (4-core
quota), CPU-only PyTorch 2.15, with 20 tokens, 7-token prefill and 13 decode steps, two pinned

byte-identical for both budgets; the 1 MiB run recorded 247 cache evictions. Two earlier local
attempts stopped before comparison: the first lacked a writable PyTorch extension-cache path,

and setting `TORCH_EXTENSIONS_DIR` resolved them. The real slice is **not run** because it has
not yet been supplied. The full suite passed **124 tests** with **11 GPU tests skipped**.

For planning only, extrapolating the earlier four-thread real-slice rates gives a **projected**
`248/2.62 + 8/0.064 + 248/2.60 + 8/0.061 ≈ 446 s` for one Mode A and one cached Mode B trace:
the inputs are prefill and decode token counts divided by the Mode A and B tok/s reported above.
Those earlier rates used a 128-token prompt on another run; trace overhead, the longer prompt,
machine load, the additional zero-budget trace and export time are excluded, so actual time may
differ substantially. No paid service is needed on the existing cloud CPU.
