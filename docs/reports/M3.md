# M3 report: Mode B, lossless entropy coding

Date: 2026-11-03. Status: done on CPU. Mode B is **bit-identical to Mode A** through the full
engine on the real 7-layer slice and on the tiny model. The GPU decode kernel is not built yet.

## What was built

| Piece | Where | What it does |
|---|---|---|
| Codec | `boilerplate/format/entropy.py` | Canonical Huffman over bytes, codes limited to 12 bits, independent blocks of 4096 symbols with bit offsets, decode by a single 4096-entry table lookup |
| Kernels | `boilerplate/kernels/csrc/boilerplate_cpu.cpp` | `huff_encode`, plus `huff_decode` with OpenMP over blocks. The layout (one table, per-block offsets, MSB-first) is the one a GPU decoder of one thread block per block needs |
| Format | `boilerplate/format/export.py`, `docs/architecture/format.md` | `T.hstream / T.hoffsets / T.hlens / T.hraw` per tensor, with dtype and shape in the manifest |
| Engine | `boilerplate/engine/weights.py` | A Mode B tensor is decoded back to its exact original bytes on first use, then goes through the Mode A path unchanged |
| Policy | `configs/policy/lossless.yaml` | Every weight Mode B |

What gets coded: for 1-byte formats (FP8 e4m3, packed FP4 pairs, e8m0 scales), every byte. For
BF16/FP16, the high byte (sign, exponent, top mantissa bit), with the low byte stored raw. FP32
tensors are left alone; they total 0.17 GB in the release.

## Gain, measured on the real slice (all 6.0 GB of it)

Every tensor of the 7-layer slice was coded, decoded, and compared byte for byte. All of them
round-trip exactly.

| tensor type | bytes | coded / original |
|---|---|---|
| routed experts, FP4 pairs (int8 storage) | 1.98 GB | **0.977** |
| routed expert scales (e8m0) | 124 MB | 0.176 |
| attention FP8 | 902 MB | 0.827 |
| shared experts FP8 | 248 MB | 0.829 |
| FP8 block scales | 1.1 MB | 0.16–0.18 |
| embedding + head BF16 | 2.65 GB | 0.674 |
| other BF16 | 18 MB | 0.67 |
| FP32 (not coded) | 28 MB | 1.0 |
| **whole slice** | **5.95 GB** | **0.795** (5.87 b/w overall) |

The slice over-weights the BF16 embedding and head, which compress best. The full model is
mostly FP4 experts and FP8 engram, which compress least.

### Engram tables (2 × 131,072 real rows sampled from the release)

| | coded bits per byte | order-0 entropy |
|---|---|---|
| FP8 rows, layer 1 | 6.64 | 6.55 |
| FP8 rows, layer 14 | 6.64 | 6.54 |
| e8m0 row scales | 1.30–1.33 | 0.92 |

So the tables come to 0.83x for the rows, 0.17x for the scales.

### Whole model (projected from the shard headers × the measured ratios above)

| role | release | Mode B |
|---|---|---|
| routed experts (FP4 + scales) | 296.0 GB | 275.1 GB |
| engram tables | 202.8 GB | 164.2 GB |
| everything else | 11.5 GB | 10.2 GB |
| **total** | **510.3 GB** | **≈ 449.5 GB (0.88x)** |

This is the honest ceiling for lossless on this checkpoint. The FP4 experts are already close to
their entropy, so there is about 2% to win there. Huffman codes each symbol in at least 1 bit,
which is why the scales stay above their entropy; rANS would close that gap, but the scales are
only 2% of the file.

## Correctness

- Engine, real slice, 256 WikiText-2 tokens: Mode B logits are **bit-identical** to Mode A
  (KL 0, max-abs 0, `bit_exact: true`).
- Tiny model: same, every layer, plus a byte-for-byte check of every tensor against the source
  (`test_mode_b_bit_exact`).
- Codec unit tests cover uint8, FP8, BF16 and FP16 inputs, and a frequency distribution that
  forces length-limiting past 12 bits (`test_entropy_roundtrip`, `test_entropy_length_limit`).

## Speed (CPU, 4 threads)

| | |
|---|---|
| decode | 532 MB/s of original bytes |
| encode | 32 MB/s (single-threaded encoder + Python frequency count; export-time only) |
| export of the 6 GB slice | 246 s |
| engine, Mode B vs Mode A | prefill 2.60 vs 2.62 tok/s; decode 0.061 vs 0.064 tok/s; load 9.7 vs 1.7 s |
| peak RSS | 12.1 GB vs 8.4 GB |

Today a Mode B tensor is decoded whole on first use and stays decoded in RAM. So it saves disk
and download size, but not memory, and memory is higher than Mode A, which can leave cold experts
on disk through mmap. Saving memory needs decoding per layer or per expert just before use (the
DFloat11 approach) on the GPU. At 532 MB/s on CPU, decoding the 6 experts a token routes to
(about 106 MB of FP4 per layer) costs about 200 ms per layer, which is too slow for CPU decoding. That is a
GPU kernel job.

## Not done / next

- GPU Huffman decode kernel (one CUDA block per 4096-symbol block, with the table in shared
  memory), fused before the FP8/FP4 GEMM, with decoding per layer to save memory.
- Optionally rANS, for the last ~1–2% on scales and FP8.
- Mode B combined with Mode C in one policy (for example, Mode B for attention and embeddings, Mode C for
  experts). The format allows it, because modes are per tensor; it is untested beyond the per-mode tests.
