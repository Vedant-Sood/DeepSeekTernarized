# M0 report: skeleton, config parser, reference harness

Date: 2026-11-03. Status: done, with one open dependency for M1 (see the end of this report).

## What was built

| Piece | Where | What it does |
|---|---|---|
| Package skeleton | `pyproject.toml`, `boilerplate/` | Installable package, `boilerplate` CLI, pytest setup |
| Source config | `configs/source.yaml` | Checkpoint id `deepseek-ai/DeepSeek-V4.1-Flash-1017`; nothing about its shape |
| Checkpoint metadata | `boilerplate/checkpoint/` | Reads `config.json`, the safetensors index and shard headers, from a local directory or a Hub repo (headers over HTTP range requests, no weight download) |
| Storage formats | `boilerplate/checkpoint/dequant.py` | FP8 e4m3 block-scaled and packed FP4 e2m1 dequant/quant; block sizes inferred from shapes; FP4 rounding is round-to-nearest-even like a hardware convert |
| Config parser | `boilerplate/config/` | Derives a `ModelSpec` from config + index + headers, cross-checks them, and reports disagreements as warnings |
| Tensor roles + size report | `boilerplate/config/roles.py`, `report.py` | Classifies every tensor (routed expert, router, engram table, ...) and reports params, bytes and bits/weight per role from the headers |
| Tiny checkpoint | `boilerplate/testing/tiny.py` | Writes a random-init checkpoint in the exact V4.1 on-disk format (names, sharding, FP8/FP4 storage) |
| Reference harness | `boilerplate/reference/` | Traces (per-layer hidden states + full logits) saved to safetensors + JSON; layer-wise comparison (cosine, rel-L2, max-abs, bit-exactness, logit KL, top-1 agreement); two backends |
| Official backend | `reference/official_backend.py` | Imports the checkpoint's own unmodified `inference/` code, converts weights with its own `convert.py`, maps HF config to `ModelArgs`, hooks each block |
| CPU kernel shim | `reference/cpu_kernels.py` | Pure-PyTorch drop-in for the reference's TileLang `kernel.py` (FP8/FP4 activation quant, FP8 and FP4 GEMM, sparse attention with sinks, Sinkhorn mixing) so the reference can run without a GPU |
| HF backend | `reference/hf_backend.py` | transformers models, for families transformers supports |

CLI:

```bash
boilerplate inspect deepseek-ai/DeepSeek-V4.1-Flash-1017 --json spec.json   # or a local dir
boilerplate make-tiny ./tiny
boilerplate reference official ./tiny --code-dir ./inference --out traces/tiny_ref
boilerplate compare traces/tiny_ref traces/tiny_modeA --min-cos 0.999
```

## Tests

`pytest`: 51 passed on CPU (Python 3.13, torch 2.15, transformers 5.22).

* Storage formats: FP4 ties-to-even and nearest rounding, pack/unpack of all 16 codes in the reference layout, FP8/FP4 quant-dequant error, block-size inference.
* Parser: the tiny checkpoint parses with no warnings and every derived field matches its config; per-role formats are verified from headers; FP4 experts account at exactly 4.25 bits/weight; removing an expert or a compressor from the index produces the expected warnings; the no-headers fallback is flagged.
* The released V4.1 `config.json`, with its tensor-name layout, parses into the right plan: 40 layers, 384 experts top-6, window-only layers 0–1, shared compressed-KV sources 2/8/14/20, indexer sources, YaRN only on compressed layers, engram, MTP, vision.
* Translating the released `config.json` with `hf_config_to_model_args` reproduces every value in the `inference/config.json` that ships beside it.
* CPU kernels: FP8 and FP4 GEMMs match matmuls on dequantized operands; quant in place matches quant-then-dequant; sparse attention matches a naive loop, including sinks and all-empty rows; Sinkhorn output is doubly stochastic.
* Harness: trace save/load round-trip is bit-exact; compare flags a perturbed layer; the HF backend traces a tiny random-init DeepSeek V3 deterministically; the official backend runs a stand-in reference package through the CPU shim with full-sequence logits and without leaking modules.

## Findings that change the plan

Details: `docs/architecture/deepseek_v41_flash.md`.

1. **The routed experts are already FP4 (4.25 bits/weight).** The 5–8× figure in the brief assumed 8–16-bit weights. Projected from config and file sizes (not measured): TQ1 experts take the checkpoint from ~510 GB to ~334 GB (≈1.5×); TQ2 ≈1.4×.
2. **About 40% of the checkpoint is two engram lookup tables (~203 GB, FP8).** The default policy keeps embedding-like tables at high precision. Ternarizing them as well would give roughly 175 GB in total (≈2.9×). Because they are lookups, they can stay mmap'd on disk, so the GPU-resident weight footprint drops from roughly 300 GB to roughly 130 GB with TQ1 experts. Whether engram tables are in scope for ternarization is a decision for later (M2 policy).
3. **Mode B will have little to compress.** Entropy coding targets exponent redundancy, and FP4/FP8 have 2/4 exponent bits. M3 will measure it rather than assume DFloat11-like gains.
4. **No mainstream runtime supports V4.1.** transformers has `deepseek_v4`, not `deepseek_v41`, and the architectures differ. The reference is the official `inference/` code. vLLM/SGLang support has not been checked yet.
5. **Not MLA.** Attention is a single shared 512-d KV head with sliding-window plus shared compressed KV and a learned top-k indexer, on a 4-way hyper-connection residual stream. The engine's attention and residual design (M1) follows this, not V3-style MLA.

## Not done in M0, and why

* **Running the real reference code.** This build container's network policy blocks `huggingface.co`, so the official `inference/` files could not be downloaded here. I read them through the Hugging Face connector, which is how the parser, config mapping and kernel shim were written and checked. The official backend is tested against a stand-in package with the same interface. Running it on the tiny checkpoint is the first M1 task once the code is available.
* **Shard headers of the real checkpoint** were not read, for the same reason. `boilerplate inspect deepseek-ai/DeepSeek-V4.1-Flash-1017` on any machine with Hub access reads them, and turns the storage table above from "per reference code" into "verified".
* **Engram, vision and DSpark tensors in the tiny checkpoint.** Engram needs the reference `engram.py` hashing and a tokenizer, so these come in M1 along with the reference code.

## M1 plan

1. Get the official `inference/` code (and tokenizer files) into the workspace, run the official backend on the tiny checkpoint with the CPU shim, and add engram + MTP to the tiny config.
2. Build a "truncated real" small model: a few real layers and experts streamed from the release with range requests, so M1 also validates on trained weights, not only on random init.
3. Mode A engine: weight loading (mmap), FP8/FP4 linears, the window + compressed-KV attention with indexer, hyper-connections, MoE routing, and a paged KV cache. Validate layer by layer against the reference traces.
