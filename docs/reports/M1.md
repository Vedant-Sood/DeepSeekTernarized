# M1 report: Mode A engine matching the reference

Date: 2026-11-03. Status: done. The Mode A engine is **bit-exact** with the official DeepSeek
reference on the tiny model and on a 7-layer slice of the real trained weights, for prefill and
for decode.

## What was built

| Piece | Where | What it does |
|---|---|---|
| Engine config | `boilerplate/engine/config.py` | Everything comes from `config.json`. It also derives the per-layer plan: which layer's compressed KV and indexer each layer reads |
| mmap weights | `boilerplate/engine/weights.py` | Every shard is memory-mapped and every tensor is a zero-copy view, so experts and engram tables are only read when used |
| Model | `boilerplate/engine/model.py` | Hyper-connections, sliding-window + compressed sparse attention with indexer and candidate blocks, engram, MoE routing (sqrtsoftplus, selection-only bias, top-k normalization and scale), RoPE/YaRN. Weights stay FP8/FP4 |
| Paged KV cache | `boilerplate/engine/kv_cache.py` | A fixed window ring per layer, plus paged compressed KV and index keys indexed by token position, with one page table per sequence. Pages are reused when a sequence is freed |
| Engram hashing | `boilerplate/engine/engram.py` | Primes, compressed token map, multipliers and per-sequence n-gram history, without the reference's sympy/transformers dependencies |
| API + CLI | `boilerplate/engine/engine.py`, `cli.py` | `Engine.load / generate / generate_text / trace`; `boilerplate trace | generate | bench | make-truncated` |
| Kernels | `boilerplate/kernels/torch_ref.py` | The official TileLang kernels' numerics in PyTorch. Used by the reference shim and as the engine's Mode A backend |
| Vendored reference | `third_party/deepseek_v41_inference/` | Official `inference/` code (MIT, rev `1bae0e10`), unmodified, so the equivalence tests run offline |
| Truncated real model | `boilerplate/testing/truncate.py` | Cuts a layer and expert subset out of the release using HTTP range requests |
| Tiny checkpoint | `boilerplate/testing/tiny.py` | Now 8 layers in the release's layout, with engram and a small tokenizer |

Design notes are in `docs/architecture/engine.md`. A step flattens the tokens of all sequences
into one batch, so projections, MoE and hyper-connections run once. Only attention is
per-sequence. A step can mix prefilling and decoding sequences. Chunked prefill (start > 0 with
several tokens) is not supported yet; the reference does not support it either.

## Validation

All comparisons use the official code running unmodified, with the same PyTorch kernels in place of
TileLang. Metrics come from `boilerplate compare`: per-layer cosine, rel-L2, max-abs and bit-exactness
on the full 4-copy residual stream, plus logit KL and top-1 agreement.

| Model | Run | Result |
|---|---|---|
| Tiny (8 layers, random init) | 40-token prefill | every layer and the logits bit-identical |
| Tiny | batch 2, 13-token prefill + 27 decode steps | bit-identical |
| Tiny | 1-token prefill + 11 decode steps | bit-identical |
| **Real weights**: layers 0,1,2,3,20,21,24 of V4.1 Flash, first 16 experts each | 590-token prefill of real text + 10 decode steps | **bit-identical**, all 7 layers and logits (KL 0, top-1 1.0) |

The tiny prompts are longer than the window (8) and than `index_topk` (8), so the ring wraps, the
indexer has to choose, and the candidate-block prefilter actually drops blocks. In the real-weight
slice, layers map to: 2 window-only, a 2:1 KV + index source, its sharer, a 1:1 KV + candidate
source, its sharer, and an index source that reads shared keys. At 590 tokens the 1:1 layers have
more compressed positions than `index_topk` = 512, so top-k selection is active. The candidate
prefilter (2048 blocks × 8) only starts dropping blocks past 16K tokens, so on real weights it runs
but keeps everything. Tiny covers the case where it drops blocks.

Other tests (`tests/test_engine.py`; 60 tests pass in total):

* Batching: three prompts of different lengths prefilled in one step and decoded together give the same greedy tokens as each run alone.
* Paged cache: page accounting is correct, and a sequence reusing freed pages and a freed slot gets logits identical to a fresh cache.
* Greedy generation equals the reference's argmax when the reference is fed the same tokens.
* Engram: primes, token map and hash ids match the reference's `NgramHashState` for prefill and decode. On the **real** tokenizer and config (checked by script, not in CI, since it needs the 6 MB tokenizer), the compressed vocab is 99,092 as the config says, the derived table sizes equal `engram_num_embeddings` (384,006,168 and 384,016,682), and hashes match the reference on 600 real tokens.

### A finding about the reference itself

The first real-weight comparison was **not** exact: differences appeared at layer 0 and grew to 75%
top-1 agreement at the logits. Layer-by-layer bisection showed the engine was not the cause. The
reference run differed *from itself*: a second run of the same reference on the same input
disagreed with the first in the same way. The first run shared the 4 CPUs with other jobs.
MKL's dynamic threading then chose a different thread count for some GEMMs, which changes the
summation order. With `MKL_DYNAMIC=FALSE` the reference is reproducible and the engine matches it
bit for bit. Boilerplate now sets this by default (`boilerplate/__init__.py`).

Two consequences for later milestones:

* One last-bit difference at layer 0 turned into 25% different argmaxes after 7 layers of this
  truncated model. Bit-exactness is a property of a fixed kernel and thread configuration, not
  something to expect across hardware. Comparisons of Modes B–D on GPU should use the tolerance
  metrics, and the Mode B "bit-identical" criterion means identical to Mode A *on the same kernels*.
* The truncated model is far more sensitive than the full one is likely to be: it is missing 33
  layers and 368 of 384 experts per layer. Its divergence numbers say nothing about real quality.

## Measured performance (CPU, correctness backend)

4 vCPUs, no GPU, PyTorch 2.15 CPU, `torch_ref` kernels, 4 threads, `boilerplate bench`:

| Model | Batch | Prompt | Prefill tok/s | Decode tok/s | Peak RSS |
|---|---|---|---|---|---|
| Tiny | 1 | 128 | 294 | 23.1 | 0.28 GB |
| Tiny | 4 | 128 | 850 | 46.2 | 0.29 GB |
| 7-layer real slice (6.0 GB on disk) | 1 | 256 | 5.6 | 0.067 | 8.35 GB |

These numbers are for a correctness backend, not the engine's real speed. The torch kernels
dequantize each FP8/FP4 weight to FP32 for every GEMM. A 2 GB LRU of dequantized weights helps the
tiny model, but the real slice's working set (~18 GB in FP32) does not fit, so every decode step
re-dequantizes every weight. Fast paths come with the M2 kernels (FP4/FP8 and ternary GEMV/GEMM on
CPU and GPU). Running the reference on the real slice took 222 s and 12.8 GB peak RSS, against
262 s and 8.8 GB for the engine trace.

## Checkpoint facts now verified from headers

`boilerplate inspect` now reads the real shard headers, which became possible because huggingface.co is
reachable from this container. They confirm every storage format and byte count in
`docs/architecture/deepseek_v41_flash.md` (routed experts 288.8 GB at 4.25 bits/weight, engram tables 202.8 GB
at 8.25). One parser false positive is fixed: engram tables legitimately use 1×32 scale blocks, and
this no longer triggers the "declared block size" warning.

## Not done in M1, and why

* **Engram forward on real weights.** The engram tables are ~100 GB each and cannot be sliced by row
  without changing the hash layout. Hashing is verified on the real tokenizer and config. The
  forward pass (lookup, gating) is bit-exact on tiny.
* **Vision tower and DSpark/MTP draft stages.** The reference's generation loop does not run them
  either (its `forward_spec` is never called). The engine loads text-only and ignores `mtp.*`.
* **HTTP server.** The CLI and Python API are in place. The OpenAI-compatible streaming server
  is next on the interface list (it is small, and `Engine.generate` already has a streaming callback).
* **Explicit expert offload policy.** Cold experts stay on disk through mmap and the page cache. A
  managed GPU/CPU expert cache needs the GPU kernels.
* **Chunked prefill**: see above.

## M2 plan

1. TQ2 / TQ1 packing with documented layouts and round-trip tests.
2. Ternary GEMV/GEMM kernels without multiplies in the inner loop, with unpack and scale fused in. C++ for CPU (AVX2/AVX-512, NEON) first, since no GPU is available here, then CUDA. Each is tested against `torch_ref` on dequantized weights.
3. Mode C: greedy residual fitting with k = 1–4, group size 128, optional GPTQ compensation. A YAML precision policy (routed experts ternarized by default).
4. Mode C vs Mode A on the tiny model and the real 7-layer slice: per-layer cosine, logits KL, effective bits per weight.
